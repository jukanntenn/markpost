# MRFC: The agent-driven development loop

Status: proposed

English | [中文](2026-08-22-agent-driven-development-loop.zh.md)

## Problem

markpost ships by direct commits to `main`: the recent history holds no pull requests at all (one release back-merge excepted), there is no issue intake — no templates, no board, no triage — and review happens, when it happens, inside an agent session with no durable record. The operating model this repository needs inverts that: the human decides, and an agent drives one hundred percent of the execution — issues in, stacks of reviewed pull requests out, merged work closed — through a loop repeatable enough to schedule. The decisions such a loop forces (which points stay human, who reviews what, how stacked pull requests and worktrees are organized, how the board reflects progress, what enforces the gates mechanically) are process design no code or spec can carry; this record is their home. The mechanical vocabulary is borrowed from the reference harness at `.local/contexts/deepseek-harness`, trimmed wherever markpost is a single-maintainer personal repository rather than an organization.

## Proposal

**Three human gates; the agent drives everything else.** Deciding what to build (an issue moving into `Ready`), approving a design (the RFC stack), and accepting delivery (the implementation stack) are the human's three decisions per non-trivial change; trivial changes keep only the delivery gate. The `Ready` move is skill discipline — the agent never advances an issue into `Ready`, and claims only issues already there — because project-board permissions cannot express that boundary; the other two gates are platform-enforced. The standing Ask-first boundary (schema migrations, new dependencies, CI and Docker changes) survives as a mandatory "Ask-first items" section in every stack's pull-request body, the human reviewer's forced-attention list. The agent pre-reviews every layer before requesting a human: a structured comment review against `AGENTS.md`, the specs, and the documentation gates. Approval belongs to the human alone — not by convention but because the machine account cannot approve its own pull requests, so the platform makes the assignment of "comment review is the agent's, approve is the human's" load-bearing.

**A machine account holds the pen.** All agent-driven GitHub operations — claiming, pushing branches, opening pull requests, commenting, landing stacks — run as a dedicated machine account (`markpost-agent`, a collaborator with a classic PAT scoped to this repository with `repo` and `project`) through `GH_TOKEN` in the agent's environment, leaving the maintainer's own `gh` login untouched for decision actions. The split buys three things the shared-identity alternative cannot: the approval gates can distinguish an agent's pre-review from the human's sign-off, the audit trail attributes every timeline action to its true driver, and the agent's blast radius is one repository rather than the whole account. Board-mutating workflows write through `GITHUB_TOKEN` where it proves to reach a user-owned Projects v2 and through a PAT secret otherwise — verified at rollout, one maintainer action if the fallback is needed.

**Issue intake by template.** Five Chinese issue templates — `Idea`, `Feature`, `Bug`, `Research`, `Task` — with blank issues disabled; each template forces a one-line statement (at most 50 visible units) above a collapsed `<details>` block holding acceptance criteria and evidence fields. Type lives in `type/*` labels applied by template frontmatter, because personal repositories have no native issue types (measured: GraphQL `repository.issueTypes` returns `null` here). A personal GitHub Project is the board: statuses `Inbox / Backlog / Ready / In progress / In review / Done / No action` and a `P0–P3` priority field. An `issue-lifecycle` workflow moves issues automatically — opened or reopened to `Inbox`; implementation activity on a resolving pull request to `In progress`; review requested to `In review`; a changes-requested review back to `In progress` only when automation set the current status, so a human's manual placement is never silently overridden; closure to `Done` or `No action` by close reason. An `issue-policy` workflow is the pull-request check: once a non-draft, non-bot pull request enters review it must carry a valid conventional-commit title, at least one `area/*` label, and correctly formed references, and every referenced issue must satisfy the template contract. Both run one Python standard-library policy script (with `unittest` coverage) that the agent also runs locally before filing — one logic, self-check and enforcement. Pull-request kinds stay in the conventional title prefix rather than labels; `area/backend|frontend|e2e|devops|docs` is the extensible starting set; no source labels, no migration machinery.

**Claiming and decomposition.** The agent claims an issue that is `Ready` and unassigned, choosing by priority then age; claiming is assignment plus a declaring comment, never a board write. Decomposition's unit is the decision, not the file: the agent enumerates the non-trivial decisions the issue forces, writes one MRFC pair per decision, and stacks the pull requests when the decisions depend on each other (schema, then API, then UI) or files them independently when they do not. Issues that clear the existing mechanical-local-edit exemption take a fast path with no RFC layer — straight to an implementation pull request, delivery gate only.

**Two-phase stacks.** An RFC stack — one `proposed/` MRFC pair per layer, each layer referencing the issue with `Related to #N` — is reviewed at the design gate; on approval it merges first, so the MRFCs land on `main` as `proposed/` and the implementation stack builds from that new `main` with stable references. Only the top implementation layer carries the closing keyword `Fixes #N`, so the issue closes exactly when the whole stack lands and stays open under a partial landing; the agent writes the board's `In progress` once, at implementation start, because lower implementation layers carry no closing reference for the lifecycle workflow to see. The implementation layer that makes a decision real — usually the top — moves that MRFC pair from `proposed/` to `implemented/` and rewrites it into the present tense in the same change. Small design gaps found during implementation amend the still-`proposed` MRFC inside the implementation pull request; a decision-level reversal stops for the human.

**Worktrees.** Each layer gets its own worktree under `.local/worktrees/<branch>/` — inside the repository's established scratch root, already excluded by both `.gitignore` and `.dockerignore`, so the skill instruction is a repository-relative path that holds wherever the repo is cloned. Branches name `rfc/<issue>-<slug>` and `impl/<issue>-<slug>`; fixes land in the worktree of the layer that introduced them, never in a downstream checkout. `prek`'s hooks are shared through the common hooks directory but resolve `prek` from `PATH` in the current worktree, so no per-worktree installer is ported (verified with a worktree commit at rollout). Version 1 runs one worktree at a time: the compose dev environment's fixed container names make environments mutually exclusive, an accepted limit until [the isolation proposal](2026-08-22-worktree-dev-environment-isolation.md) lands.

**The session resume protocol.** Gates are asynchronous, so every agent session opens with triage: enumerate the machine account's open pull requests and their official stacks; for each, if the review decision is approved, checks are green, and no changes are outstanding, the gate has passed — merge the stack and continue the next phase (RFC stack merged means implementation starts; implementation stack merged means cleanup and closure); if reviews returned feedback, run the response loop; if nothing is in flight, claim the next `Ready` issue. Version 1 starts sessions by explicit human request; version 2 adds a scheduled poll of the same protocol, only after manual rounds have proven stable.

**Deliverables and evidence.** Every implementation layer ships code, tests, and the documentation its change touches — a new spec page adds its `specs/index.md` row in the same pull request. The pull-request body states its references, the Ask-first items, and evidence: commands run with outcomes, mapped against the issue's acceptance conditions, and Playwright screenshots for UI changes. Animated-interaction evidence is deliberately deferred to [the browser-GIF proposal](2026-08-22-browser-gif-evidence-chain.md); screenshots carry v1 acceptance.

**Feedback propagation.** Every review comment is verified against the code before it is acted on — a reviewer naming the right symptom may still misdiagnose the cause. An accepted fix lands on the layer that introduced the problem and propagates up-stack by merge-forward, the default because it rewrites no reviewed history and keeps approvals valid; the rebase path stays available for deliberate use under lease protection with a full re-audit afterward. Each fix is its own commit, never an amendment of reviewed work; replies go into the original review thread naming the commit that carries the fix.

**Landing.** Stacks land only through GitHub's native stack object and `gh stack merge <stack> --yes --merge`, after a preflight that re-queries the official stack and judges every layer independently — open, non-draft, approved, checks green. A native merge blocker is resolved through the owning pull request or stops the run; there is no fallback to per-PR `gh pr merge` with manual retargeting. Completion means every layer reports `MERGED`; a separate cleanup pass deletes a branch only after no open pull request still bases on it, then removes the worktree.

**Guardianship in two stages.** The repository keeps merge commits as the only merge method — squash and rebase buttons off — because stacked layers keep exact diffs against their bases only when parents land as merge commits, and per-layer conventional history is already enforced at commit time. Version 1 branch protection: require a pull request with one approving review, dismiss stale approvals on new pushes, require conversation resolution, include administrators, forbid force pushes to `main`; pull-request branches stay unprotected so lease-protected stack pushes still work. No required checks in v1 — the path-filtered workflows skip markdown-only pull requests entirely, and a required check that never reports would strand every RFC stack; the agent's triage verifies the check rollup itself. Version 2 adds an `if: always()` conclusion job to each of the five pull-request workflows and sets those five as required checks, closing the gap mechanically. `deleteBranchOnMerge` stays false; verified manual cleanup covers partial landings. No merge queue — a single maintainer has no concurrent-landing pressure.

**Skills carry the workflow.** Six new skills own the mechanics — `dev-loop` (resume protocol and phase state machine), `stacked-prs` (worktrees, branch naming, layer creation, linking), `merging-stacked-prs` (landing), `responding-to-review` (feedback propagation), `code-review` (pre-review standard), `filing-issues` (template discipline with policy self-check) — joining `iterating`, `writing-mrfcs`, and `commit` as the full pipeline from discussion to landed work. The root `AGENTS.md` gains one compact section naming the gates, the machine account, and the reference-discipline rules, linking to `dev-loop` for everything else; this record holds the rationale. The transformation itself lands as one plain pull request — the loop's bootstrap — and moves this record to `implemented/` in that same change.

## Alternatives considered

**Share the maintainer's GitHub identity for agent operations.** Zero setup, but the approval gates lose their mechanical meaning — a shared identity cannot distinguish the agent's pre-review approve from the human's sign-off — the audit trail cannot attribute actions, and the agent would hold a token over the whole account. The machine account costs one manual setup and returns enforcement, attribution, and a one-repository blast radius.

**A GitHub App instead of a machine account.** The formal choice with the smallest scopes, rejected on measurement: this `gh` build's `gh auth login` offers no App-credentials flow (web OAuth, `--with-token`, environment token only), so an App means a locally maintained private-key-to-installation-token minting script against one-hour expirations for every session. Proportionate for an organization with platform tooling, not for a personal repository.

**Fewer human gates.** Two gates (agent adopts issues on its own) or one (agent self-reviews designs, human approves delivery only) each trade away a decision the maintainer explicitly wanted to keep: what gets built ranks with how it is designed; a design error discovered only at delivery costs the whole implementation. Three gates cost roughly three touchpoints per non-trivial change, and the fast path trims trivial work to one.

**Human review of every pull request, agent review as reference only.** The safest reading of "human or agent review", but it converts the loop back into human-paced serial review; the chosen model has the agent pre-review first and the human approve, with Ask-first categories forcing human attention where the standing boundary already demands it.

**One mega-stack (RFC layers at the bottom, implementation above), landing once.** A single review context, but an RFC revision during the design gate would cascade-rebase the implementation layers above it, and the two gates blur inside one stack. The two-phase architecture lets each gate map to one merge and keeps every stack small.

**All implementation layers carrying `Fixes #N`.** Correct `In progress` timing from the workflow alone, but the bottom layer's merge would close the issue moments before the rest of the stack lands — invisible in a full landing, wrong in a partial one. The top-layer-only keyword plus one agent-written `In progress` is correct in both.

**Worktrees outside the repository.** Physical isolation that relies on no ignore lists, and the reference harness's actual model. Rejected on measurement: the claimed hard reason — build-context pollution — is already covered (`.dockerignore` excludes `.local/`), the remaining costs are cosmetic, and `.local/worktrees/` keeps skill instructions repository-relative and collects the project's artifacts under one cleanable root.

**External-sibling worktrees.** Same trade measured from the other side; lost for the same reasons — the repo-relative instruction and the established `.local/` scratch convention outweigh physical isolation whose residual risk the Ask-first boundary on new tooling already contains.

**The full label taxonomy.** Exactly one `kind/*` and at least one `area/*` per pull request, issues on native types, source labels, migration machinery — the reference's organization-scale answer. markpost's conventional-commit titles already carry kind where it is queried, personal repositories lack native issue types, and a single machine author makes source labels redundant; the trimmed set keeps `area/*` for review triage and drops the rest.

**Rebase as the default propagation history.** Compact, but it rewrites reviewed branches as a matter of course, invalidating approvals and comment anchors on every feedback round. Merge-forward preserves the reviewed history; rebase remains a deliberate, lease-protected escape hatch.

**Squash merges.** A linear `main`, but stacked children compute their diffs against their base branches; squashed parents change the commits those children sit on and pull parent changes into every child diff, dismantling the per-layer review structure the loop exists to provide.

**Branch protection with required checks from day one.** Mechanically complete immediately, but the path-filtered workflows skip markdown-only changes, so every RFC stack would wait forever on checks that never report. The staged plan ships the approval gates first — usable today, zero CI changes — and adds conclusion jobs before requiring checks.

**Scheduled driving from day one.** Fully unattended immediately, but a first-round failure would repeat unattended. Manual sessions validate the loop end to end first; the scheduler wraps the identical triage protocol afterward.

## Acceptance criteria

Phase 0 (bootstrap, one plain pull request): the five issue templates and `config.yml`, the pull-request template, the policy script with its tests, both workflows, the six skills, the label set, the board with its statuses and priority field, the machine account as collaborator, merge-commit-only repository settings, and v1 branch protection are all live; the documentation gates pass with this record moved to `implemented/` and both companion proposals in place.

Phase 1 (first loops, manually kicked): one trivial issue completes the fast path end to end — claimed, implemented, approved by the human, landed, issue auto-closed to `Done` on the board, branches and worktree cleaned with the zero-dependent check observed; one non-trivial issue completes the full loop — RFC stack reviewed and landed at the design gate, implementation stack built from the new `main`, delivered and landed at the delivery gate, the MRFC pair moved to `implemented/` by the finalizing layer. The policy check demonstrably fails a non-compliant pull request and the lifecycle workflow demonstrably refuses a backward transition from a human-set status.

Phase 2 (mechanical completion): each of the five pull-request workflows reports its conclusion job on every pull request regardless of paths; those five are required checks and an unreviewed or red stack cannot land; the scheduled poll drives at least one issue through the loop with no human kick; the GIF and isolation proposals have each either landed or been rejected on their own record.

## Risks

Board automation depends on token reach: `GITHUB_TOKEN` against a user-owned Projects v2 is unverified, and the PAT-secret fallback is one more long-lived credential to rotate. The dev environment remains mutually exclusive across worktrees until the isolation proposal lands, serializing verification that needs it. Three gates are three human touchpoints per non-trivial change — the price of the control being real, reduced but not eliminated by the fast path. `gh stack` is an external extension over a young native API; if either shifts, landing hard-stops rather than degrading to unsafe manual merges. The agent's pre-review shares its author's blind spots — it is a filter and a briefing, not a substitute for the approval that follows. The scheduled driver (phase 2) can repeat a failing action unattended between human visits; it is gated behind proven manual rounds precisely for that. And the `Ready` gate remains skill discipline rather than platform enforcement — a board misjudgment by a future agent is detectable in the audit trail (the machine account made the move) but not preventable by permissions alone.
