# MRFC: Cloudflare deployment guide and spec alignment

Status: implemented

English | [中文](2026-08-22-cloudflare-deployment-guide.zh.md)

> Port topology superseded by [origin on host-port 443 behind the shared host Caddy gateway](2026-08-23-origin-port-443-shared-gateway.md) — 2053 turned out to be a cache-disabled port; everything else here stands.

## Problem

The SaaS production instance (`markpost.cc`, VPS origin behind Cloudflare) needed an operating guide an operator can execute end to end — dashboard steps, host prep, deploy, verify. [`docs/deployment.md`](../../../docs/deployment.md) had grown into a full multi-environment lifecycle reference (acceptance, dev, staging, production, Ansible internals, operational tasks, image-tag semantics) too long to serve as that runbook. Worse, the specs owning the Cloudflare design facts had drifted from what the deploy tree actually ships: [`specs/backend/cloudflare.md`](../../../specs/backend/cloudflare.md) described a `:7157` Caddy with a `443:7157` mapping as an unimplemented target, called the Caddyfile template a tracked follow-up, and claimed `cloudflare_cidrs` was still a placeholder — while [`Caddyfile.production.j2`](../../../devops/ansible/templates/Caddyfile.production.j2) ships `:2053`, the origin is reached through an Origin Rule rewriting 443 → 2053, and the real CIDRs sit in `group_vars/production/vars.yml`. Any runbook written from the specs would contradict the repo; any written from the repo would contradict the specs. The deepest drift was the client-IP mechanism: the specs describe a pure XFF-append chain defended at the TCP layer, but the template's `header_up X-Forwarded-For {http.request.header.CF-Connecting-IP}` rewrite supersedes that chain — and the specs' own described design cannot work as written, because gin (`SetTrustedProxies` loopback-only) walks XFF right-to-left and would return the Cloudflare edge hop as the client IP for every visitor, collapsing the IP-keyed limiters.

## Decision

**A focused production runbook, the old guide frozen in place.** [`docs/deployment-cloudflare.md`](../../../docs/deployment-cloudflare.md) (with its zh twin) covers the Cloudflare lifecycle only — one-time dashboard setup (proxied A record, Full strict, Origin CA certificate, Origin Rule 443 → 2053), one-time VPS prep (cert placement, host firewall locked to Cloudflare CIDRs on 2053), required vault secrets with acquisition steps (GitHub OAuth app, Cloudflare API token), pinned-release deploy, verification through the edge, and CIDR resync — stating operations without design rationale, which links to the spec. `docs/deployment.md` stays at its path with a frozen banner redirecting production work to the new guide (the `PRINCIPLES.md` freeze precedent), retaining dev/staging/acceptance as a reference snapshot; its three inbound links (both languages) stay valid. No word budget is attached: `scripts/doc_budgets.manifest.json` bounds agent-instruction files only, and the operations-only constraint is the editorial ceiling.

**Specs align to deployed reality, verified against sources.** `specs/backend/cloudflare.md` and `rate-limiting.md` (both languages) now describe what the templates ship: the `:2053` topology with the Origin Rule, the deployed `Caddyfile.production.j2` shape (`auto_https off`, Origin CA cert paths, per-block `trusted_proxies` + `header_up`), the real `cloudflare_cidrs` home and its firewall mirror, and the client-IP mechanism as a single-value relay — Caddy's user header operations run after its default forwarded-header handling (caddy `modules/caddyhttp/reverseproxy/reverseproxy.go`, header ops applied in the proxy loop), so the XFF reaching Go is always the single Cloudflare-asserted `CF-Connecting-IP`; the collapse is required for correctness, because gin's `validateHeader` (gin `gin.go`) returns the first untrusted IP from the right and loopback-only trust would otherwise yield the edge hop. Trust anchors are Cloudflare's edge overwrite of `CF-Connecting-IP` plus the host firewall's CIDR allowlist; the residual exposure — a firewall bypass can forge the header and the rewrite propagates it — is recorded instead of the earlier, inaccurate defense-in-depth claim. The rejection of `gin.PlatformCloudflare` stands: it performs no CIDR check at the application layer.

## Alternatives considered

**Archive-rename the old guide and reuse the `deployment.md` name for the new one.** It lost: three inbound links across both languages would churn for naming semantics, while the in-place freeze matches the `PRINCIPLES.md` precedent and keeps the snapshot one hop from its readers.

**Keep extending the single multi-environment guide.** It lost: length was the trigger for this decision; the Cloudflare path specifically needs console-exact steps a maintainer can execute without wading through dev/staging internals.

**Fix the templates to match the specs** — drop `header_up`, restore the pure XFF-append chain the specs described. It lost on source verification: with gin trusting loopback only, the appended chain `<real-client>, <cloudflare-hop>` makes `ClientIP()` return the Cloudflare edge hop for every request; the deployed rewrite is the mechanism that keeps the IP-keyed limiters functional.

**Adopt `gin.PlatformCloudflare`.** It lost as before: no CIDR check at the application layer, so any direct reach to the port can forge the header; the deployed design keeps the check at the packet layer where the firewall already enforces it.

## Consequences

All seven documentation gates pass with the new pair, the banners, and the rewritten spec sections; the format of the client-IP claims is source-citable (caddy/gin repositories under `~/Workspace/contexts/`), replacing prose that described a mechanism that cannot work. The two-guide state carries a duplication cost — the frozen snapshot and the live runbook overlap on production facts — accepted because the banner redirects and the snapshot is explicitly unmaintained; when dev/staging procedures next change, their guide must be unfrozen or split rather than edited in place. The spec rewrite also surfaced and recorded an honest residual risk the old prose masked: header authenticity rests on the firewall, so the CIDR resync duty (firewall + `cloudflare_cidrs`) is load-bearing, and the runbook states it as recurring work. At decision time the production origin does not yet serve traffic (edge answers, origin 502) — the runbook is the path to a green `https://markpost.cc/api/v1/health`, and the frozen guide still carries the origin IP in prose, a publication consideration the runbook avoids by using a placeholder.
