# Backend Internationalization

English | [中文](i18n.zh.md)

## Tech Stack

The backend uses `gin-contrib/i18n` (v1.2.2) + `nicksnyder/go-i18n/v2` (v2.6.0) for server-side message localization. Error messages and response strings are translated according to the client's `Accept-Language` header. Locale files are TOML and live in `backend/locales/`.

## Locale File Organization

```
backend/locales/
├── active.en.toml         ← English (sourceLanguage; goi18n extract output, kept)
├── active.zh-Hans.toml    ← Simplified Chinese
├── active.zh-Hant.toml    ← Traditional Chinese (Taiwan)
├── active.ja.toml         ← Japanese
└── translate.*.toml       ← scratch untranslated files (not in git; deleted once translated)
```

- **BCP 47 naming**: locale tags follow BCP 47 (`en`, `zh-Hans`, `zh-Hant`, `ja`) and match the `Accept-Language` header.
- **Default language `en`**: English backs up any missing translation.
- **Supported languages**: en / zh-Hans / zh-Hant / ja, with room to grow (adding a language means adding an `active.<locale>.toml` file).
- **`active.en.toml` is kept**: it is the baseline file of the goi18n extract/merge workflow (see "The full translation workflow" below).
- **`translate.*.toml` never enters git**: deleted as soon as translation completes; `active.*.toml` files are the source of truth.

## Message Format (template interpolation)

TOML format; each entry is a TOML table storing the translated string in its `other` field:

```toml
["error.validation_min_length"]
other = "{{.Field}} must be at least {{.Min}} characters"

["post.created"]
one = "{{.Count}} post created"
other = "{{.Count}} posts created"
```

- **Template interpolation**: Go [text/template](https://pkg.go.dev/text/template) syntax `{{.Key}}`, with values passed via `LocalizeConfig.TemplateData`.
- **Plurals**: CLDR plural forms (`one` / `other` / `few` / `many`, etc.), selected via `LocalizeConfig.PluralCount`.

## Message ID Naming Conventions

All lowercase with underscores, grouped by feature prefix:

| Category                  | Pattern                  | Examples                                                   |
| ------------------------- | ------------------------ | ---------------------------------------------------------- |
| Error messages            | `error.<code>`           | `error.invalid_credentials`, `error.not_found`             |
| Field validation messages | `error.validation_<tag>` | `error.validation_required`, `error.validation_min_length` |
| Success / notice messages | `<feature>.<action>`     | `auth.logout_success`, `post.created`                      |
| Health checks             | `health.<key>`           | `health.running`                                           |

**Success messages carry no `error.` prefix** (`auth.logout_success`, not `error.logout_success`).

## The Dual-Source Structure

Messages have two sources that cooperate at runtime:

| Source                            | Content                                        | Role                             |
| --------------------------------- | ---------------------------------------------- | -------------------------------- |
| **`ErrCode.Message` in code**     | English `DefaultMessage` (ID + Other included) | Authoritative fallback source    |
| **Locale files (active.\*.toml)** | Per-language translations                      | Provide non-English translations |

### Runtime rendering (apierr)

`apierr` renders with `ginI18n.MustGetMessage`, pointing `DefaultMessage` at the ErrCode's own Message:

```go
func renderMessage(c *gin.Context, code *service.ErrCode, data map[string]any) string {
    msg := ginI18n.MustGetMessage(c, &i18n.LocalizeConfig{
        DefaultMessage: code.Message,   // in-code English fallback
        TemplateData:   data,           // {{.Field}} {{.Min}} and friends
    })
    if msg == "" {
        return code.Message.Other       // last-resort fallback: the English original
    }
    return msg
}
```

**Rendering logic** (go-i18n's four-level `Localize` fallback):

1. Look in the requested language's (e.g. zh-Hans) locale file first → if it hits, the translation is used
2. Not found → fall back to the default language's (en) locale file
3. Still not found → use `DefaultMessage` (the in-code English)
4. DefaultMessage is nil → returns empty (intercepted by apierr's `code.Message.Other` last-resort fallback)

**Why `active.en.toml` is kept**: its content duplicates the in-code DefaultMessage (both English) without conflicting. It exists as the baseline of the goi18n extract/merge workflow — extract produces it, and merge uses it as the base to generate the other languages' translate files.

## The Message Literal Hard Constraint

### Rule: every field of a message must be a string literal

goi18n extract AST-scans Go source for `i18n.Message` / `i18n.LocalizeConfig` CompositeLits. Field values are recognized only as:

- **String literals** (`*ast.BasicLit`): `"hello"` ✅
- **String concatenation** (`*ast.BinaryExpr`): `"a" + "b"` ✅
- **References to string constants** (`*ast.Ident` pointing at a const declaration): ✅ (the convention still demands literals only, to avoid ambiguity)

**Not recognized**: variables, function return values, non-string constants.

### Correct form

```go
var ErrInvalidCredentials = &ErrCode{
    Message: &i18n.Message{              // ← an i18n.Message literal
        ID:    "error.invalid_credentials",
        Other: "Invalid username or password",  // ← a literal; extract picks it up
    },
}
```

**The key point**: the nested `&i18n.Message{...}` inside the ErrCode struct is itself a literal; goi18n extract's `ast.Walk` recurses into it and **extracts it correctly** (the extractor scans every `i18n.Message`-typed CompositeLit, whatever struct wraps it).

### Incorrect form

```go
// ❌ a variable — extract cannot see it
msg := "Invalid username or password"
var ErrInvalidCredentials = &ErrCode{
    Message: &i18n.Message{ID: "error.invalid_credentials", Other: msg},
}

// ❌ a function call — extract cannot see it
Other: generateMessage("invalid_credentials"),
```

### Duplicate ID detection

goi18n extract has built-in duplicate detection: two messages sharing an ID with differing content make extract fail with `duplicate message ID: xxx`. This built-in guard keeps message IDs globally unique.

## The Full Translation Workflow

### Installing the goi18n command

```bash
go install -v github.com/nicksnyder/go-i18n/v2/goi18n@latest
```

### Scenario 1: adding a message (the everyday development case)

A developer wrote a new `&i18n.Message{ID:"post.created", Other:"Post created"}` in code:

```bash
# 1. Extract every message into active.en.toml
goi18n extract

# 2. Generate the to-translate files (including the new message)
goi18n merge active.*.toml

# 3. Translate translate.zh-Hans.toml / translate.zh-Hant.toml / translate.ja.toml

# 4. Merge the translations into active.*.toml
goi18n merge active.*.toml translate.*.toml

# 5. Delete the scratch to-translate files
rm translate.*.toml
```

### Scenario 2: adding a language (Korean ko, for example)

```bash
# 1. Create an empty file
touch translate.ko.toml

# 2. Fill it with the messages to translate
goi18n merge active.en.toml translate.ko.toml

# 3. Translate translate.ko.toml

# 4. Rename it to active
mv translate.ko.toml active.ko.toml

# 5. Register the loading in code
bundle.LoadMessageFile("active.ko.toml")
```

### Scenario 3: editing an existing message

The English original changed (e.g. `Other` goes from "Invalid username or password" to "Username or password is incorrect"):

```bash
# 1. extract updates active.en.toml (the message's hash changed)
goi18n extract

# 2. merge flags the entries needing retranslation (hash mismatch)
goi18n merge active.*.toml

# 3. Translate the changed entries
# 4. Merge
goi18n merge active.*.toml translate.*.toml
```

### The hash field mechanism

Each message in a `translate.*.toml` generated by `goi18n merge` carries `hash = "sha1-..."` (the sha1 of the message content). When the English original changes, the hash changes, and merge recognizes "this entry needs retranslation".

### CI integration suggestion

Add a CI check: if `goi18n extract` leaves a diff in `active.en.toml`, new messages skipped the full translation workflow — CI fails and prompts the developer to finish the translations.

## Language Detection

The language is detected from the `Accept-Language` HTTP header (gin-contrib/i18n's `defaultGetLngHandler`). When the header is missing or names an unsupported language, the default language `en` backs up.

## Code Usage

Handlers fetch translated strings with `ginI18n.MustGetMessage` (TemplateData interpolation supported):

```go
message := ginI18n.MustGetMessage(c, &i18n.LocalizeConfig{
    DefaultMessage: &i18n.Message{
        ID:    "auth.logout_success",
        Other: "Logged out successfully",
    },
})
```

`DefaultMessage` supplies the English fallback. Error messages are rendered uniformly by `apierr` (see the apierr package contract in [error-handling.md](./error-handling.md)).

## Configuration

i18n is configured at startup in `cmd/server/main.go`:

```go
r.Use(ginI18n.Localize(ginI18n.WithBundle(&ginI18n.BundleCfg{
    RootPath:        "./locales",
    AcceptLanguage:  []language.Tag{language.English, language.Chinese, language.Japanese},
    DefaultLanguage: language.English,
    UnmarshalFunc:   toml.Unmarshal,
    FormatBundleFile: "toml",
})))
```
