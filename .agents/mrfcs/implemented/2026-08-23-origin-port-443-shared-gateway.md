# MRFC: Origin on host-port 443 behind the shared host Caddy gateway

Status: implemented

English | [中文](2026-08-23-origin-port-443-shared-gateway.zh.md)

## Problem

The SaaS origin ran on host port 2053 behind a Cloudflare Origin Rule rewriting 443 → 2053 (the topology recorded in [the Cloudflare deployment guide MRFC](2026-08-22-cloudflare-deployment-guide.md)). Edge caching never worked through the real zone: every response — including default-cached extensions (woff2, CSS) served with `Cache-Control: public, max-age=31536000, immutable` — returned `CF-Cache-Status: DYNAMIC`, capping the site at the origin's 3 Mbps line and voiding the CDN as the load-bearing design ([caching spec](../../../specs/backend/caching.md)). The root cause is in the Cloudflare docs snapshot (`fundamentals/reference/network-ports.mdx`): every proxied HTTPS port except 443 is listed under "Ports supported by Cloudflare, but with caching disabled" (2052, 2053, 2082, 2083, 2086, 2087, 2095, 2096, 8880, 8443), and re-enabling any of them via `additional_cacheable_ports` is Enterprise-only (`cache/how-to/cache-rules/settings.mdx`). With Full (strict) as the SSL mode, 443 is the only origin port that can carry edge caching on the Free plan. The original port decision had been validated for rule availability ("Origin Rules are available on every plan, Free included") but never cross-checked against the cache-port matrix; the capacity loadtests verified MISS → HIT origin-direct, so the gap surfaced only when the zone went under live test. A second constraint surfaced with it: the VPS is not single-service (a second container already publishes 8443; a fleet of subdomain proxies serves `*.bytehome.fun`), and 443 can be bound by exactly one process.

## Decision

**The origin is host-port 443, terminated by the host's systemd Caddy acting as a shared gateway; markpost joins it as one site block.** The gateway (already running on the production host with `import /etc/caddy/conf.d/*.caddy`) presents the existing 15-year `*.markpost.cc` Origin CA certificate — the playbook copies it to `/etc/caddy/certs/markpost/` (root:caddy, 0640) — and reverse-proxies `markpost.cc` to `127.0.0.1:8080`. The markpost container's Caddy drops TLS entirely: [`Caddyfile.production.j2`](../../../devops/ansible/templates/Caddyfile.production.j2) serves plain HTTP on the internal port, published loopback-only (`127.0.0.1:8080:2053`), so the only possible peer is the host gateway. The client-IP relay is unchanged in mechanism: `CF-Connecting-IP` passes through the gateway untouched (not a hop-by-hop header) and the container Caddy still rewrites `X-Forwarded-For` from it; `trusted_proxies` shrinks from the Cloudflare CIDR list to `private_ranges` (the gateway's NAT'd bridge address is the peer). The Origin Rule is deleted from the zone; the host firewall swaps "2053 from Cloudflare CIDRs" for "443 from Cloudflare CIDRs"; `cloudflare_cidrs` in `group_vars/production/vars.yml` stays the documented home of the list for the firewall but feeds no template. Further services join by dropping their own `conf.d` site block — ports bind exclusively, hostnames do not; services that need no edge caching can stay on the cache-disabled ports (that is what 8443 hosts today).

## Alternatives considered

**Stay on 2053 and make the port cacheable with a rule.** It lost: `additional_cacheable_ports` is Enterprise-only, and no Free-plan Cache Rule overrides the port gate — confirmed live with the Cache Rule active and matching (`Eligible for cache`, `starts_with(http.request.uri.path, "/p-")`) while every response stayed `DYNAMIC`.

**Publish the markpost container directly on host 443, no gateway.** It lost: one port binds one process, so it would freeze the multi-service plan (the second service already exists) and couple every future service to markpost's compose lifecycle; the host Caddy gateway was already running and idle.

**Cloudflare Tunnel (no inbound ports at all).** It lost for now: a cloudflared daemon per host plus a rewrite of the firewall / trusted-proxies / CIDR design the spec had just stabilized, and the local docs snapshot does not cover caching behavior through tunnels — it would need live verification first. Worth revisiting if inbound-port management ever becomes the burden.

## Consequences

Edge caching becomes reachable at all; acceptance is the `verify-cf.sh` MISS → HIT sequence plus the woff2 canary (default-cached, rule-independent). The flip needs a short maintenance window in a fixed order — delete the Origin Rule first, then run the playbook, which stages the gateway site before recreating the container; deploy.yml's final edge verification passes only when both halves are live. One TLS hop leaves the container (healthcheck is plain HTTP everywhere now — `tls_profile: http`, matching dev/staging) and one is added on the host; the Origin CA cert has two homes (`~/docker/markpost/certs/` as the source the playbook copies, `/etc/caddy/certs/markpost/` as what the gateway reads). Origin-direct loadtests against production must tunnel to `127.0.0.1:8080` instead of hitting `:2053`; staging keeps its 2053 shape, so loadtest defaults stand. The client-IP relay's residual exposure narrows: forging `CF-Connecting-IP` now requires being Cloudflare (firewall-enforced on 443) or already being on the host, because the container port is loopback-only. The [Cloudflare deployment guide MRFC](2026-08-22-cloudflare-deployment-guide.md) is superseded in its port topology and cross-links here; its client-IP analysis stands.
