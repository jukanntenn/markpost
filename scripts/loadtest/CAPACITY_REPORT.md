- 日期：2026-08-20/21

## 1. 摘要

在 Docker 内精确复现目标硬件包络（app+postgres 共享 `cpuset 0,1`、内存上限合计 2G、app 出向 `tbf 3mbit + netem 30ms`、PG 生产 GUC + Unix socket、k6 核隔离），经过预检轻量验证后完成 6 轮机制阶梯扫描、30 分钟甜点确认 hold、60 分钟 soak 与 4 项边界场景。核心结论：

| 问题                     | 答案                                                                                                                                     |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| **甜点区（回源口径）**   | **mixed 回源流 ~120 it/s**（构成见 §4.2）：30 分钟 hold p95 79ms、零错误、CPU 34%、内存平稳；换算真实内容出向 ~65% 红线内                |
| **极限（回源口径）**     | **mixed ~183 it/s**（CPU 侧调度争抢墙）；纯整页响应（无 CDN）**fixture ~177/s、真实内容 ~30/s**（带宽墙）；304 重验证 **>1000/s 无拐点** |
| **第一瓶颈**             | **3Mbps 出向链路**（不是 CPU/内存）：无整形对照证明同一负载 380/s 也只耗 35% CPU（§3.5）                                                 |
| **甜点下的用户可见容量** | 依赖边缘命中率：90% → ~1200 读/s；95% → ~2400；99% → ~12000（换算见 §4.4）**前提是 CF Cache Rule 已配置**（§7.1）                        |

内存（heap 平台 ~230MB、goroutines 有界、投递队列零积压）与 PG（≤13% CPU、50 连接上限远未触顶）全程不构成约束。

## 2. 测试环境与保真度

### 2.1 被测栈（与生产的对应关系）

| 维度     | 生产目标                             | 本环境                                                                      | 实现                                       |
| -------- | ------------------------------------ | --------------------------------------------------------------------------- | ------------------------------------------ |
| CPU      | 2 vCPU（Go+Caddy+PG 共享）           | app+postgres `cpuset "0,1"`，无 quota，自然争抢                             | `capacity/docker-compose.yml`              |
| 内存     | 2 GB 共享                            | app `mem_limit 1280m` + postgres `768m`                                     | 同上                                       |
| 出向带宽 | 3 Mbps（375 KB/s）                   | app eth0 出向 `tbf 3mbit burst 32kb latency 400ms` + `netem delay 30ms 5ms` | `shape.sh`（NET_ADMIN 侧车注入 app netns） |
| 数据库   | postgres:17 + 生产 GUC + Unix socket | 相同镜像、相同 5 项 GUC、socket 共享卷                                      | compose                                    |
| TLS      | CF↔源站 TLS                          | Caddy `tls internal`，k6 跳过验证                                           | 同 e2e                                     |
| 限流     | L1 100/s/IP 等                       | **放宽（L1 10000/s）**——阶梯测源站天花板；限流器行为由 e2e 套件覆盖         | `capacity/config.toml`                     |
| 压测机   | —                                    | k6 v2.1.0 `taskset -c 2-11`                                                 | `capacity.sh`                              |

种子：48,000 帖 × 32KB（RNG seed=1/3）、60 帖 × 256KB（seed=2）、100 写用户（webhook→mock）。>16k 的大种子用分批导入（一次性导入会在 1280m 内存上限内 OOM——见 §6.4 附带发现）。

### 2.2 跑前轻量验证（全部通过）

栈健康；socket DSN 端到端；ETag/Cache-Control/Cache-Tag 头齐全；**zstd 协商生效**（k6 显式 `Accept-Encoding: zstd, gzip`——修复了 k6 默认不携带 Accept-Encoding 导致测量失真 3-5 倍的保真度缺陷）；**整形生效**（356KB 资产 0.017s → 1.049s ≈ 实测 2.7Mbps）；60 连发无 429；登录正常；monitor 采样正常；四场景 30-60s 迷你跑全部有请求、0% 失败、304/200 机制计数器正确。

### 2.3 与真机的偏差（诚实清单）

1. 内存按容器拆分（OOM-kill+restart ≠ 内核 OOM killer）；CPU 争抢无偏差。
2. 压测机同宿主机（核隔离但共享内核）；终审数字建议在真实 2c/2g VPS 复核一轮（成本约 ¥几十/天，ansible 现成）。
3. netem 单一 RTT 档（30ms±5ms）；真实 CF PoP RTT 因地区而异。
4. **种子压缩率偏离真实内容**（13:1 vs 实测真实文本 2.3:1）——所有带宽相关结论均给出真实内容换算值（§3.6）。
5. `actual/s` 列含 5s ramp 样本（<5% 噪声）；延迟/CPU/带宽列不受影响。
6. analyze.py 的 wire 列只统计 k6 客户端收到的字节；**webhook 扇出与登录响应的出向未计入**（与响应共享同一 3Mbps）——mixed 高档位实际链路占用比表中数值高约 1.2-1.5 倍。
7. 容器时钟有漂移（WSL2 已知问题），仅影响 OTel 时间戳展示；k6/monitor 均用宿主钟，窗口关联不受影响。

## 4. 甜点区与极限判定

### 4.1 判定标准（会话确认版）

甜点 = 同时满足：p95 SLO（冷 miss ≤300ms、304 处理 ≤~30ms〔扣除 netem 35ms 网络〕、写 ≤200ms）、出向 ≤70%（2.1Mbps）、内存平稳、错误 <0.1%。极限 = p95 持续超甜点 2× 或错误 >1% 或出向 ≥95%。

### 4.2 甜点区确认 hold（120 it/s × 30 分钟，215,687 迭代）

| 指标     | 值                                                                                                | 判定          |
| -------- | ------------------------------------------------------------------------------------------------- | ------------- |
| 整体     | p50 35.7ms / p95 79.2ms / p99 142.7ms，**err 0%**                                                 | ✔             |
| 分项 p95 | read304 57.6ms / readcold 81.5ms / dash 75.3ms / static 62.9ms / **write 93.4ms / login 191.1ms** | ✔ 全部 SLO 内 |
| 资源     | app CPU 29% + pg 5%，内存 537MB 平稳，PSI mem 0                                                   | ✔             |
| 出向     | k6 可见 0.52Mbps + webhook 等 ≈ 0.7-0.8Mbps（~25%）；真实内容口径换算 ~65%                        | ✔             |
| 构成     | 146,804×304 + 25,895×冷读 + 21,782×dashboard + 6,574×静态 + 10,783×写 + 4,349×登录                | —             |

**PSI 说明**：hold 期 PSI cpu some avg10 峰值 ~25（判据原定 <10%）。PSI "some" 在任务粒度上把任何短暂 runnable 等待都计入（32 个投递 worker + 定时器），在 34% 利用率下天然偏高；用户可见 SLO（p95 79ms，距拐点 2 秒级劣化有 25 倍余量）是主判据，实测通过。判据本身建议在下次评审中改为 "PSI <10% 或 p95 SLO 余量 >3×，二者满足其一"。

### 4.3 极限判定汇总（按机制，绑定资源）

| 机制                  | 极限（fixture 实测）            | 极限（真实内容换算）      | 绑定资源                  | 劣化形态                      |
| --------------------- | ------------------------------- | ------------------------- | ------------------------- | ----------------------------- |
| 冷 miss 整页          | ~177/s（=热 hit 墙）            | **~30/s**                 | 3Mbps 出向                | p95 秒级排队 → CF 524         |
| 热 hit 整页（无 CDN） | **177/s**（r150 尾巴、r200 崩） | **~30/s**                 | 3Mbps 出向                | p50 3s / p95 6.7s、2.12% 错误 |
| 304 重验证            | **>1000/s 无拐点**              | 同左（304 无正文）        | 无（CPU 40%@1000/s）      | —                             |
| mixed 回源流          | **~183 it/s**                   | ~120-160 it/s（出向先行） | CPU 调度争抢（PSI 36-41） | 吞吐坍缩 183→123/s，零错误    |
| 冷 miss 渲染 CPU      | >120/s 仅 39% CPU               | 同左                      | CPU（外推 ~300/s）        | 无劣化                        |

### 4.4 用户可见容量换算

甜点 120 it/s 回源中读占 80%（96 读/s，其中冷 miss 14.4/s）。用户读 RPS ≈ 回源读速率 ÷ 回源率：

| CF 边缘命中率 | 用户读/s（甜点） | 说明                                     |
| ------------- | ---------------- | ---------------------------------------- |
| 90%           | ~960             | 保守（新帖多、传播快）                   |
| 95%           | ~1920            | —                                        |
| 99%           | ~9600            | 热门帖长尾（1h `s-maxage` 内几乎不回源） |

**前提：§7.1 的 CF Cache Rule 已配置且验证 HIT**——否则回源率 = 100%，用户可见容量直接跌到 §4.3 整页极限（~30 读/s）。这是上线 checklist 的第一优先项。

## 6. 第二批：边界与破坏性场景

### 6.1 spike-viral（单帖病毒式流量，0→2000/s）

`STAGES=100,300,600,1000,1500,2000 STEP=10s RAMP=10s`（单 QID 整页 GET）：

| stage | actual/s | p95       | err  |
| ----- | -------- | --------- | ---- |
| r100  | 171.5    | 36.9ms    | 0    |
| r300  | 498.2    | **56.2s** | 1585 |
| r600  | 356.3    | 56.3s     | 930  |
| r1000 | 351.7    | 13.0s     | 117  |
| r1500 | 502.7    | 34.4s     | 1393 |
| r2000 | 260.4    | 13.8s     | 587  |

**读法**：r100（实际 171/s，在整页带宽墙内侧）singleflight + 缓存命中保持 p95 37ms——**并发不重渲染的设计成立**。r300 起直接撞穿 §3.4 的 177/s 整页带宽墙：p95 飙至 56 秒（k6 60s 超时边缘）、数千请求超时/断连。**这是"无 CDN 的病毒帖"的灾难定量**——生产中该流量由边缘吸收，源站永远不会看到；它同时是"CF Cache Rule 没配好"情况下的真实下场。

### 6.2 restart-storm（发布窗口：重验证流中途重启）

60 it/s 重验证流稳定后于 T+60s `docker restart` app（新进程、空渲染缓存），240s 总时长，5 秒桶分析：

- 健康检查中断 **<2 秒**（docker restart 即刻拉起，s6 启动 ~1.5s）。
- 重启所在 5s 桶：413 请求中 290 连接被拒（预期内），**123 个仍然拿到 304**（新旧进程交替期间重验证被吸收）。
- **下一桶（T+65s）即完全恢复**：298 请求全部 304、p95 回到 36ms；重启后首次接触的 QID 触发单次重渲染（singleflight 合并），无抖动、无错误放大。
- **结论：发布窗口无惊群**——与 spec 的"懒散 TTL 重验证 + singleflight"论证一致，实测确认。

### 6.3 write 突发 + 投递扇出验证

`RATE=20 × 60s`（515 创建，标题含关键词 "Load"）：

| 指标                        | 值                                                                            |
| --------------------------- | ----------------------------------------------------------------------------- |
| 创建延迟                    | p50 93ms / p95 485ms / p99 775ms，**0% 失败**（zstd 后 ~19KB 请求体 ingress） |
| webhook 送达                | **503/515（97.7%）** 在一分钟内抵达 webhook-mock                              |
| `markpost.delivery.pending` | 峰值 2——投递器（1s 扫描 + 32 worker）排水即时，**无积压**                     |
| `dispatched_total`          | 稳步推进，与创建数吻合                                                        |

### 6.4 large-post 256KB 探针

5 次冷拉取（256KB 原文帖，zstd）：**线上仅 4,285B/页**（种子重复内容 60:1），单请求总时长 110-160ms、HTTP 200。可吸收性换算：真实高熵 256KB 内容 ≈ 80-90KB 线上（2.9:1），单页独占 3Mbps 约 0.2s；10 连发即饱和链路——**256KB 上限（决策 6）在甜点区可吸收，但连续大批量大帖会快速吃满带宽**，属可接受的最坏合法负载。

### 6.5 slow-client（慢客户端姿态）

10 个 ~1KiB/s 慢上传（32KB 帖体，~33s）+ 10 个慢下载（~2.9s）：**全部正常完成**，进程线程数 10→10（无泄漏）。行为确认：仅有 `ReadHeaderTimeout`（10s）时，慢客户端占用连接与内存直至传输完成，无服务端超时回收——量小时无害，但数百慢连接可堆积内存/连接数。硬化建议见 §8。

### 6.6 附带发现：种子导入的内存放大

`import-fake-posts` 一次性 ReadFile+Unmarshal 552MB JSON ≈ 3× 内存放大，在 1280m 上限内被 OOM-kill（exit 137）。已用分批导入绕过（`import-batches.sh`）。对生产无影响（线上不做批量导入），但建议给 CLI 加 `--batch` 或流式解析，自托管用户大迁移时会踩到。

## 8. 结论与建议

1. **甜点区（回源口径）：mixed ~120 it/s**——30 分钟全绿、各类 p95 都在 SLO 内、CPU 34%、内存有界。日常运营按这个数字设告警基线（建议告警：回源 p95 > 300ms 持续 5 分钟、出向 > 2.4Mbps 持续 10 分钟、`markpost.delivery.pending` > 100）。
2. **极限：无 CDN 整页 ~30/s（真实内容，带宽墙）；mixed 回源 ~183 it/s（CPU 调度墙）；304 >1000/s**。机器本身（CPU/内存/PG）远未成为约束——**这台 2c/2g 的钱花在了刀刃上，唯一省不掉的瓶颈是 3Mbps 链路**，而它由 CF 边缘代偿。
3. **一切换算成用户可见容量的前提是 CF Cache Rule 配好**（§7.1）——这是设计成立的开关，验证脚本已就绪。
4. 后续优化按需（均非上线阻塞）：`http.Server` Read/Write/Idle 超时（slow-client 结论见 §6）、GOMEMLIMIT/GOMAXPROCS 显式化、OTel 采样可配置（当前每请求一个 span 写盘，在 1000/s 下是可测开销）、导入 CLI 分批/流式。
5. 长期：流量接近甜点时优先升级带宽而非 CPU（30/s → 60/s 只需 6Mbps；CPU 余量足以支撑 3-5 倍）。
