# MRFC: The agent-driven development loop

Status: implemented

English | [中文](2026-08-22-agent-driven-development-loop.zh.md)

## Problem

markpost shipped by direct commits to `main`: the history held no pull requests at all (one release back-merge excepted), there was no issue intake — no templates, no board, no triage — and review happened, when it happened, inside an agent session with no durable record. The operating model the repository needed inverted that: the human decides, and an agent drives one hundred percent of the execution — issues in, stacks of reviewed pull requests out, merged work closed — through a loop repeatable enough to schedule. The decisions such a loop forced (which points stay human, who reviews what, how stacked pull requests and worktrees are organized, how the board reflects progress, what enforces the gates mechanically) are process design no code or spec can carry; this record is their home. The mechanical vocabulary is borrowed from the reference harness at `.local/contexts/deepseek-harness`, trimmed wherever markpost is a single-maintainer personal repository rather than an organization.

## Decision

**Three human gates; the agent drives everything else.** Deciding what to build (an issue moving into `Ready`), approving a design (the RFC stack), and accepting delivery (the implementation stack) are the human's three decisions per non-trivial change; trivial changes keep only the delivery gate. The `Ready` move is skill discipline — the agent never advances an issue into `Ready`, and claims only issues already there — because project-board permissions cannot express that boundary; the other two gates are platform-enforced once branch protection is on (a maintainer settings step, below). The standing Ask-first boundary (schema migrations, new dependencies, CI and Docker changes) survives as the mandatory "Ask-first items" section of the pull-request template, the human reviewer's forced-attention list. The agent pre-reviews every layer before requesting a human: a structured comment review against `AGENTS.md`, the specs, and the documentation gates. Approval belongs to the human alone — not by convention but because the machine account cannot approve its own pull requests, so the platform makes "comment review is the agent's, approve is the human's" load-bearing.

**A machine account holds the pen.** All agent-driven GitHub operations — claiming, pushing branches, opening pull requests, commenting, landing stacks — run as a dedicated machine account (`gh2bda`, a collaborator on this repository and deliberately reusable across the maintainer's agent-driven projects) through a classic PAT with `repo` and `project` scopes supplied as `GH_TOKEN` in the agent's environment, leaving the maintainer's own `gh` login untouched for decision actions. Classic tokens are not repository-scoped — the account's collaboration list, not the token, bounds the blast radius, so the account gains access only where a loop runs. The split buys three things the shared-identity alternative cannot: the approval gates distinguish an agent's pre-review from the human's sign-off, the audit trail attributes every timeline action to its true driver, and the agent's blast radius is those collaborated repositories rather than the whole human account.

**Issue intake by template.** Five Chinese issue templates — `Idea`, `Feature`, `Bug`, `Research`, `Task` — with blank issues disabled; each template forces a one-line statement (at most 50 visible units) above a collapsed `<details>` block holding acceptance criteria and evidence fields. Type lives in `type/*` labels applied by template frontmatter, because personal repositories have no native issue types (measured: GraphQL `repository.issueTypes` returns `null` here). A personal GitHub Project is the board: statuses `Inbox / Backlog / Ready / In progress / In review / Done / No action` live in a custom `Loop status` field (the project's default `Status` field cannot be deleted or API-edited — measured against both `deleteProjectV2Field` and the option-edit surface — so it stays unused and hidden in views), beside a `P0–P3` `Priority` field. The `issue-lifecycle` workflow moves issues automatically — opened or reopened to `Inbox`; implementation activity on a resolving pull request to `In progress`; review requested to `In review`; a changes-requested review back to `In progress` only when automation set the current status, recorded in a marker comment so a human's manual placement is never silently overridden; closure to `Done` or `No action` by close reason. The `issue-policy` workflow is the pull-request check: once a non-draft, non-bot pull request enters review it must carry a valid conventional-commit title, at least one `area/*` label, and correctly formed references, and every referenced issue must satisfy the template contract. Both run one Python standard-library policy script (`.github/issue-management/policy.py`, 32 `unittest` cases wired into prek) that the agent also reads against before filing — one logic, self-check and enforcement. Pull-request kinds stay in the conventional title prefix rather than labels; `area/backend|frontend|e2e|devops|docs` is the extensible starting set; no source labels, no migration machinery. The board writes are active: `config.json` points at project number 1 with `requireProject: true`, and the lifecycle workflow authenticates with the `MARKPOST_PROJECT_TOKEN` secret (the machine account's classic PAT), because `GITHUB_TOKEN` has no permission scope for user-owned Projects v2 (measured: actionlint's scope list exposes no such grant), making that PAT the only board-write path — every write it makes is recorded as the `gh2bda` actor, which the marker-comment guard reads back.

**Claiming and decomposition.** The agent claims an issue that is `Ready` and unassigned, choosing by priority then age; claiming is assignment plus a declaring comment, never a board write. Decomposition's unit is the decision, not the file: the agent enumerates the non-trivial decisions the issue forces, writes one MRFC pair per decision, and stacks the pull requests when the decisions depend on each other (schema, then API, then UI) or files them independently when they do not. Issues that clear the existing mechanical-local-edit exemption take a fast path with no RFC layer — straight to an implementation pull request, delivery gate only.

**Two-phase stacks.** An RFC stack — one `proposed/` MRFC pair per layer, each layer referencing the issue with `Related to #N` — is reviewed at the design gate; on approval it merges first, so the MRFCs land on `main` as `proposed/` and the implementation stack builds from that new `main` with stable references. Only the top implementation layer carries the closing keyword `Fixes #N`, so the issue closes exactly when the whole stack lands and stays open under a partial landing; the agent writes the board's `In progress` once, at implementation start, because lower implementation layers carry no closing reference for the lifecycle workflow to see. The implementation layer that makes a decision real — usually the top — moves that MRFC pair from `proposed/` to `implemented/` and rewrites it into the present tense in the same change (this record did exactly that in the change that implemented it). Small design gaps found during implementation amend the still-`proposed` MRFC inside the implementation pull request; a decision-level reversal stops for the human.

**Worktrees.** Each layer gets its own worktree under `.local/worktrees/<branch>/` — inside the repository's established scratch root, already excluded by both `.gitignore` and `.dockerignore`, so the skill instruction is a repository-relative path that holds wherever the repo is cloned. Branches name `rfc/<issue>-<slug>` and `impl/<issue>-<slug>`; fixes land in the worktree of the layer that introduced them, never in a downstream checkout. `prek`'s hooks are shared through the common hooks directory but resolve `prek` from `PATH` in the current worktree, so no per-worktree installer was ported. Worktrees run one at a time until [the isolation proposal](../proposed/2026-08-22-worktree-dev-environment-isolation.md) lands: the compose dev environment's fixed container names make environments mutually exclusive.

**The session resume protocol.** Gates are asynchronous, so every agent session opens with triage: enumerate the machine account's open pull requests and their official stacks; for each, if the review decision is approved, checks are green, and no changes are outstanding, the gate has passed — merge the stack and continue the next phase (RFC stack merged means implementation starts; implementation stack merged means cleanup and closure); if reviews returned feedback, run the response loop; if nothing is in flight, claim the next `Ready` issue. Sessions start by explicit human request; the scheduled poll of the identical protocol is a named follow-up, added only after manual rounds prove stable.

**Deliverables and evidence.** Every implementation layer ships code, tests, and the documentation its change touches — a new spec page adds its `specs/index.md` row in the same pull request. The pull-request body states its references, the Ask-first items, and evidence: commands run with outcomes, mapped against the issue's acceptance conditions, and Playwright screenshots for UI changes. Animated-interaction evidence is deferred to [the browser-GIF proposal](../proposed/2026-08-22-browser-gif-evidence-chain.md); screenshots carry current acceptance.

**Feedback propagation.** Every review comment is verified against the code before it is acted on — a reviewer naming the right symptom may still misdiagnose the cause. An accepted fix lands on the layer that introduced the problem and propagates up-stack by merge-forward, the default because it rewrites no reviewed history and keeps approvals valid; the rebase path stays available for deliberate use under lease protection with a full re-audit afterward. Each fix is its own commit, never an amendment of reviewed work; replies go into the original review thread naming the commit that carries the fix.

**Landing.** Stacks land only through GitHub's native stack object and `gh stack merge <stack> --yes --merge`, after a preflight that re-queries the official stack and judges every layer independently — open, non-draft, approved, checks green. A native merge blocker is resolved through the owning pull request or stops the run; there is no fallback to per-PR `gh pr merge` with manual retargeting. Completion means every layer reports `MERGED`; a separate cleanup pass deletes a branch only after no open pull request still bases on it, then removes the worktree.

**Guardianship.** The repository's merge method is merge commits only, and version 1 branch protection is require a pull request with one approving review, dismiss stale approvals on new pushes, require conversation resolution, include administrators, forbid force pushes to `main` — both are maintainer settings steps recorded here as the loop's configuration. No required checks yet: the path-filtered workflows skip markdown-only pull requests entirely, and a required check that never report would strand every RFC stack; the agent's triage verifies the check rollup itself in the meantime. The follow-up that closes the gap is named below (conclusion jobs). `deleteBranchOnMerge` stays false; verified manual cleanup covers partial landings. No merge queue — a single maintainer has no concurrent-landing pressure.

**Skills carry the workflow.** Six skills own the mechanics — `dev-loop` (resume protocol and phase state machine), `stacked-prs` (worktrees, branch naming, layer creation, linking), `merging-stacked-prs` (landing), `responding-to-review` (feedback propagation), `code-review` (pre-review standard), `filing-issues` (template discipline) — joining `iterating`, `writing-mrfcs`, and `commit` as the full pipeline from discussion to landed work. The root `AGENTS.md` carries one compact Development Loop section naming the gates, the machine account, and the reference discipline; this record holds the rationale.

## Alternatives considered

**Share the maintainer's GitHub identity for agent operations.** Zero setup, but the approval gates lose their mechanical meaning — a shared identity cannot distinguish the agent's pre-review approve from the human's sign-off — the audit trail cannot attribute actions, and the agent would hold a token over the whole account. The machine account costs one manual setup and returns enforcement, attribution, and a one-repository blast radius.

**A GitHub App instead of a machine account.** The formal choice with the smallest scopes, rejected on measurement: this `gh` build's `gh auth login` offers no App-credentials flow (web OAuth, `--with-token`, environment token only), so an App means a locally maintained private-key-to-installation-token minting script against one-hour expirations for every session. Proportionate for an organization with platform tooling, not for a personal repository.

**Fewer human gates.** Two gates (agent adopts issues on its own) or one (agent self-reviews designs, human approves delivery only) each trade away a decision the maintainer explicitly wanted to keep: what gets built ranks with how it is designed; a design error discovered only at delivery costs the whole implementation. Three gates cost roughly three touchpoints per non-trivial change, and the fast path trims trivial work to one.

**Human review of every pull request, agent review as reference only.** The safest reading of "human or agent review", but it converts the loop back into human-paced serial review; the chosen model has the agent pre-review first and the human approve, with Ask-first categories forcing human attention where the standing boundary already demands it.

**One mega-stack (RFC layers at the bottom, implementation above), landing once.** A single review context, but an RFC revision during the design gate would cascade-rebase the implementation layers above it, and the two gates blur inside one stack. The two-phase architecture lets each gate map to one merge and keeps every stack small.

**All implementation layers carrying `Fixes #N`.** Correct `In progress` timing from the workflow alone, but the bottom layer's merge would close the issue moments before the rest of the stack lands — invisible in a full landing, wrong in a partial one. The top-layer-only keyword plus one agent-written `In progress` is correct in both.

**Worktrees outside the repository.** Physical isolation that relies on no ignore lists, and the reference harness's actual model. Rejected on measurement: the claimed hard reason — build-context pollution — is already covered (`.dockerignore` excludes `.local/`), the remaining costs are cosmetic, and `.local/worktrees/` keeps skill instructions repository-relative and collects the project's artifacts under one cleanable root.

**External-sibling worktrees.** Same trade measured from the other side; lost for the same reasons — the repo-relative instruction and the established `.local/` scratch convention outweigh physical isolation whose residual risk the Ask-first boundary on new tooling already contains.

**The full label taxonomy.** Exactly one `kind/*` and at least one `area/*` per pull request, issues on native types, source labels, migration machinery — the reference's organization-scale answer. markpost's conventional-commit titles already carry kind where it is queried, personal repositories lack native issue types, and a single machine author makes source labels redundant; the trimmed set keeps `area/*` for review triage and drops the rest.

**Rebase as the default propagation history.** Compact, but it rewrites reviewed branches as a matter of course, invalidating approvals and comment anchors on every feedback round. Merge-forward preserves the reviewed history; rebase remains a deliberate, lease-protected escape hatch.

**Squash merges.** A linear `main`, but stacked children compute their diffs against their base branches; squashed parents change the commits those children sit on and pull parent changes into every child diff, dismantling the per-layer review structure the loop exists to provide.

**Branch protection with required checks from day one.** Mechanically complete immediately, but the path-filtered workflows skip markdown-only changes, so every RFC stack would wait forever on checks that never report. The staged plan ships the approval gates first — usable with zero CI changes — and adds conclusion jobs before requiring checks.

**Scheduled driving from day one.** Fully unattended immediately, but a first-round failure would repeat unattended. Manual sessions validate the loop end to end first; the scheduler wraps the identical triage protocol afterward.

**Reading the board's status actor from GitHub timeline events.** The reference queries timeline metadata to learn who set a status; the exact event types are under-documented and fragile to depend on. The marker comment — the workflow records every write it makes — provides the same guard with plain REST data.

## Consequences

The loop's repository half ships complete in this change: five issue templates with `config.yml`, the pull-request template, the policy script and its 32-case suite wired into prek, both workflows, the six skills, the compact `AGENTS.md` section, and this record's own lifecycle move — the bootstrap pull request exercised the basic PR mechanics it introduces. Activation outside the repository is nearly complete: the machine account exists with its PAT and collaborator access, the personal Project carries the `Loop status` and `Priority` fields, the `MARKPOST_PROJECT_TOKEN` secret is set, and `config.json` is flipped — remaining are the maintainer settings of merge-commits-only and the version 1 branch protection, taken when the bootstrap pull request merges. The `type/*` and `area/*` labels exist from this change's setup commands. First-loop verification — one trivial issue through the fast path and one non-trivial issue through both gates — is the acceptance the design was built against; the policy suite demonstrably fails a non-compliant pull request and the transition planner refuses backward moves from human-set statuses (both pinned by unit tests).

Accepted costs and standing risks: board automation authenticates with a long-lived PAT secret (`GITHUB_TOKEN` measured as unable to write user-owned Projects v2), one more credential to rotate; the dev environment stays mutually exclusive across worktrees until the isolation proposal lands; three gates are three human touchpoints per non-trivial change, reduced but not eliminated by the fast path; `gh stack` is an external extension over a young native API, and if either shifts, landing hard-stops rather than degrading to unsafe manual merges; the agent's pre-review shares its author's blind spots — it is a filter and a briefing, not a substitute for the approval that follows; and the `Ready` gate remains skill discipline rather than platform enforcement — a board misjudgment by a future agent is detectable in the audit trail but not preventable by permissions alone.

Named follow-ups, each with its trigger: per-workflow conclusion jobs and the five required checks (after the first loops run); the scheduled poll of the triage protocol (after manual rounds prove stable); [browser GIF evidence](../proposed/2026-08-22-browser-gif-evidence-chain.md) (when humans repeatedly re-verify interaction claims by hand); and [worktree development-environment isolation](../proposed/2026-08-22-worktree-dev-environment-isolation.md) (when full-stack verification contention actually bites).
