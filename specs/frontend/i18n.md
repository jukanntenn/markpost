# Frontend Internationalization

English | [中文](i18n.zh.md)

This document defines the frontend i18n architecture. Backend i18n lives in [backend/i18n.md](../backend/i18n.md); the frontend-backend contract is at the end of this document.

## Technology stack

The frontend uses [next-intl](https://next-intl.dev/) (v4.7.0) for client-side message localization, in **pure client mode** — no `getRequestConfig`, `next-intl/plugin`, or `i18n/request.ts` (those are server-side assembly, unavailable under a pure static export; see [build.md](./build.md) §3).

> Source basis (next-intl source): `NextIntlClientProvider` is a `'use client'` component (`NextIntlClientProvider.tsx:1`) that works from its `locale` + `messages` props alone, with no server dependency. `getRequestConfig` / `i18n/request.ts` are "server-only" (`configuration.mdx:16`). The static export skips them and passes props to the provider directly.

## Supported locales

Aligned with the backend, four locales (BCP 47 tags):

| Tag       | Language                     | Default |
| --------- | ---------------------------- | ------- |
| `en`      | English                      | ✅      |
| `zh-Hans` | Simplified Chinese           |         |
| `zh-Hant` | Traditional Chinese (Taiwan) |         |
| `ja`      | Japanese                     |         |

```typescript
// src/i18n/constants.ts
export const availableLocales = ["en", "zh-Hans", "zh-Hant", "ja"] as const;
export type Locale = (typeof availableLocales)[number];
export const defaultLocale: Locale = "en";
```

> **BCP 47 alignment**: the frontend uses `zh-Hans` / `zh-Hant` (distinguishing the scripts), matching the backend's locale tags. Requests send the current locale directly in `Accept-Language`, and the backend matches it exactly. The script-agnostic `zh` tag is not used.

## Locale files

```
src/i18n/locales/
├── en.json         English (baseline)
├── zh-Hans.json    Simplified Chinese
├── zh-Hant.json    Traditional Chinese
└── ja.json         Japanese
```

One JSON file per locale, nested objects grouped by namespace:

```json
{
  "dashboard": {
    "postKey": {
      "title": "Post Key",
      "description": "Use this key to..."
    }
  },
  "common": {
    "save": "Save",
    "cancel": "Cancel"
  }
}
```

### Translation key naming

Dot-separated with a feature prefix, consistent with the backend message-ID style:

- `dashboard.postKey.title` — the dashboard feature, post key section
- `login.username` — the login page
- `common.save` — shared translations

Namespaces mirror the route structure and the component organization.

## Locale detection and persistence

### Detection priority

```typescript
// src/utils/i18n.ts
// matchesLocale reports whether a BCP 47 tag matches one of our supported
// locales. Chinese is special-cased: zh-Hans matches zh-CN/zh-SG (Simplified),
// zh-Hant matches zh-TW/zh-HK (Traditional).
function matchesLocale(tag: string, locale: Locale): boolean {
  const lower = tag.toLowerCase();
  if (lower === locale.toLowerCase()) return true;
  if (locale === "zh-Hans") return lower === "zh-cn" || lower === "zh-sg";
  if (locale === "zh-Hant")
    return lower === "zh-tw" || lower === "zh-hk" || lower === "zh-mo";
  if (locale === "en") return lower.startsWith("en");
  if (locale === "ja") return lower.startsWith("ja");
  return false;
}

export function getDefaultLocale(): Locale {
  if (typeof window === "undefined") return "en";
  // 1. localStorage
  const stored = localStorage.getItem(STORAGE_KEY);
  if (stored && availableLocales.includes(stored as Locale))
    return stored as Locale;
  // 2. browser languages, matched against the supported tags
  for (const candidate of navigator.languages) {
    for (const locale of availableLocales) {
      if (matchesLocale(candidate, locale)) return locale;
    }
  }
  // 3. fall back to en
  return "en";
}
```

Detection order: the stored preference in localStorage first; then `navigator.languages` matched against the supported tags (`zh-Hans` also matches `zh-CN` / `zh-SG`; `zh-Hant` also matches `zh-TW` / `zh-HK` / `zh-MO`); `en` as the final fallback.

### Persistence

```typescript
export function persistLocale(locale: Locale): void {
  localStorage.setItem("locale", locale);
}
```

The preference **lives in localStorage only** — no cookie is written (the backend detects locale from the `Accept-Language` header, not a cookie).

## Dynamic message loading

Switching locale dynamically imports the matching JSON file (a separate build-time chunk, loaded on demand):

```typescript
export async function loadMessages(locale: Locale) {
  return (await import(`@/i18n/locales/${locale}.json`)).default;
}
```

## Provider assembly (pure client-side bootstrap)

`LocaleProvider` is a `'use client'` component wrapping the application in `NextIntlClientProvider`. It **receives no serverLocale / serverMessages props** — the root layout calls no server i18n API.

```tsx
// src/components/providers/LocaleProvider.tsx
"use client";

export function LocaleProvider({ children }: { children: React.ReactNode }) {
  const [locale, setLocaleState] = useState<Locale>(defaultLocale);
  const [messages, setMessages] = useState<AbstractIntlMessages>({});
  const [ready, setReady] = useState(false);

  // after hydration: read the stored locale and load its messages chunk
  useEffect(() => {
    const stored = getDefaultLocale();
    loadMessages(stored).then((m) => applyMessages(stored, m));
  }, [applyMessages]);

  const setLocale = useCallback(async (newLocale: Locale) => {
    const m = await loadMessages(newLocale);
    applyMessages(newLocale, m);
    persistLocale(newLocale);
  }, []);

  return (
    <LocaleContext.Provider value={{ locale, setLocale, availableLocales }}>
      {ready ? (
        <NextIntlClientProvider locale={locale} messages={messages}>
          {children}
        </NextIntlClientProvider>
      ) : (
        <AppShellSkeleton />
      )}
    </LocaleContext.Provider>
  );
}
```

**Until the first messages chunk resolves, children stay unmounted** and a neutral `AppShellSkeleton` renders instead — no `useTranslations` call runs with empty messages, so users see a neutral skeleton rather than untranslated keys flashing past. `applyMessages` also publishes the locale and messages to module-level slots (`src/i18n/current.ts`, `src/i18n/messages.ts`) so the non-React API client can send `Accept-Language` and resolve error-message text.

> The root layout calls no `getLocale()` / `getMessages()` (those are `next-intl/server` APIs, unavailable under a pure static export). See the Provider Stack in [architecture.md](./architecture.md).

## Usage in components

Use the `useTranslations(namespace?)` hook from next-intl:

```typescript
import { useTranslations } from "next-intl";

function PostKeySection() {
  const t = useTranslations("dashboard.postKey");
  return <h2>{t("title")}</h2>;
}
```

The namespace argument of `useTranslations` is optional — omitting it returns all messages. Namespaces support dot nesting (`useTranslations("dashboard.postKey")`).

`useLocale()` returns the current locale (from the provider's `locale` value).

## Translation workflow

Frontend locale files are **maintained by hand**, with `en.json` as the baseline. The catalog is small (about 185 keys per locale) — hand maintenance suffices.

Adding a translation key: add the entry in `en.json` → translate it into `zh-Hans.json` / `zh-Hant.json` / `ja.json`.

> The backend uses the goi18n extract/merge workflow (see [backend/i18n.md](../backend/i18n.md)); the frontend brings in no extraction tooling (next-intl binds to none, and the added complexity buys nothing).

## Frontend-backend contract

| Dimension        | Rule                                                                                                                                      |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Locale set       | identical on both sides: en / zh-Hans / zh-Hant / ja                                                                                      |
| Tags             | identical on both sides: BCP 47                                                                                                           |
| Language relay   | the frontend API client sends `Accept-Language: <current locale>` on every request; the backend translates error messages per this header |
| Message-ID style | identical on both sides: dot-separated feature prefixes (frontend `login.username`, backend `error.invalid_credentials`)                  |

The user picks a language → `persistLocale` stores it in localStorage → the API client reads the current locale → every request carries the `Accept-Language` header → the backend answers with error messages in that language.
